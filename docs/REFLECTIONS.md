# 思考与补充：对需求的理解、质疑与扩展

> 对应验收标准第 9 条「写出 5 点以上自己的思考，对上述要求进行补充，业务上、技术上都可」
> 共 14 条（第 12、13 条是拿到真实数据与真实 OCR 后补的，第 14 条是被质询 AR/AP 后补的）。每条给「现象/问题 → 我的判断 → 落地做法」，不做空泛议论。

---

## 1. 这个需求本质不是"文档解析"，而是"账务数据的可信变更"

题目罗列的是 10 个功能点，看起来像一条 ETL 流水线。但把场景放回财务室就发现：**错误代价是不对称的**。

- 少提一笔费用：财务对账时发现漏项，补上即可，成本是一小时。
- 多提一笔 / 金额错一位 / AR·AP 方向反了：**账已经记进去了**。要冲销、要跟对方代理对账、可能触发客户争议，成本是一天到一周，且伤信誉。

标题里的"智能账单助手"给了一个乐观暗示——做得越自动越好。我认为正确的产品定位是 **"自动化的对账助理 + 高召回的人审分流器"**：机器负责 80% 无歧义的单，剩下 20% 不是"失败"，而是它的第二个产品功能——**把不确定性整理成人能 30 秒决策的形式**。

这个判断决定了整个架构：所有"不确定"都必须有出口（`PENDING_REVIEW`），而不是被"最可能的答案"填平。如果只按功能清单做，很容易写出一个"看起来很智能、每单都给你一个答案、但错的地方你看不出来"的系统——这在笔试里能拿分，上线当天就会被财务关掉。

## 2. OCR 字符混淆：检测应该做，"自动修复"是个陷阱

题目要求校验 `0/O`、`1/I` 这类识别错误。直觉做法是"检测到就修"，但金额字段上这个直觉是错的。

`4O.OO` 到底该修成 `40.00` 还是 `4.00`？取决于原文印刷体，而 OCR 已经把它糊掉了。如果系统擅自修：修对了没人知道，修错了账单入账，且**没有留下任何"我改过"的痕迹**——这是最坏的一种自动化。而且混淆检测本身也有假阳性：`O` 可能真的是字母（`THC-O` 这种费率代号），`I` 可能是罗马数字。

我的做法：**分层处置，金额与单号永不自修**。

| 字段类 | 检测到混淆 | 处置 |
|---|---|---|
| 金额、单据编号、箱号、提单号 | 是 | `V-OCR_CONFUSION`(warn) → 强制 `PENDING_REVIEW`，原文与可疑字符位置一并抛给人 |
| 币种、付款方式 | 是 | 归一后若仍非法才 warn；`USD`→`USO` 这类可用白名单纠偏（因为候选集封闭、可穷举，纠错是**验证**不是**猜测**） |
| 费用名、交易方 | 是 | 只记 info，交给模糊匹配兜 |

关键区别在于**候选集是否封闭**：币种只有 180 个合法值，改错的概率可以由白名单验证；金额是无限空间，任何"修复"都是发明。这条界线我单独写成了配置项和执行顺序（`validate/ocr_repair.py` 只返回 finding，永不返回值）。

## 3. AR/AP 不是单据属性，是「主体 × 单据方向」的向量

题目特意写了"不能仅根据 Debit Note 或 Credit Note 直接判断"，这句话信息量很大——它在暗示一个常见错误：把 DN 当 AR、CN 当 AP 硬编码。

真实业务里，同一张 Debit Note 在起运港代理账上是 AP（对方收我钱），在目的港代理账上是 AR（我收对方钱）。**单据类型只决定符号，交易方向才决定主体**。所以判定必须先解一个"谁在向谁收费"的关系：

```text
d = +1  (entity == issuer，我方开单 → 向外收)
d = -1  (entity == recipient，对方开单 → 向外付)
d =  0  (entity 不在双方 → 不可判)
```

还有一个题目没提但财务会追问的点：**Credit Note 的落账方向**。通行做法有两种——"对侧科目登记"（冲减 AP 时记在 AR 侧，mirror）和"同侧红字"（same_side，金额记负）。两种都对，取决于客户的 ERP 习惯（SAP 常用红字、部分自研系统用 mirror）。我没有替客户选，而是做成 `credit_note_policy` 配置项，默认 mirror，并在审计里注明"按 mirror 口径落账"。**需求里没规定的地方，暴露成配置比替客户决定更专业**——这也是我做这份卷子时最想说的一句话。

## 4. "更新账单"的难点不是匹配，是「区分没提到和改成空」

题目说"只修改输入材料明确要求变更的字段，未明确修改的字段继承原账单值"。这句话落在代码上，比看起来难。

难点在于**三种"空"长得一模一样**：

| 情况 | 输入材料里 | 正确处置 |
|---|---|---|
| 材料没提这个字段 | 抽不到值 | **继承原值** |
| 材料明确写 `Payment Term: /` | 抽到空字符串 | 应该理解为"清空"？还是"未填"？ |
| 材料写了但抽不出来 | 抽不到值 + 该区域有 OCR 失败 | **不能继承，转人工** |

如果实现成"`new_value is not None` 才覆盖"，第二种会静默继承（可能漏掉客户真正的清空意图），第三种会静默继承（把抽取失败伪装成"未变更"）——后者是**最危险的一类 bug：系统以为自己在保守，实际在丢失信息**。

我的做法是给每个字段挂 `Provenance`（抽取器 + 原文 span + 置信度），让"有没有证据"变成可判定的：

```python
changed = (prov is not None) and (normalized_new != normalized_old)
```

- 无 `prov` → 未提及 → 继承。
- 有 `prov` 且值不同 → 显式变更 → patch，并写进 `ai_reasoning`。
- 有 `prov` 但置信度低于阈值 → **不 patch，转人工**（`P-LOW_CONFIDENCE`）。

换句话说，**"能证明"和"抽到了"必须分开**。这也是我用 `BillEntry.provenance` 而不是一个记录级 `source_file` 的原因：一条费用里的金额来自 OCR 表格、币种来自邮件正文、付款方式来自历史账单继承——三种来源混在一起时，记录级溯源等于没有溯源。

## 5. 版式多样性是长期成本，简历式"写死正则"必然崩

题目给了几张样例单据，但没说"只支持这几种版式"。真实场景是：几百家代理，每家一套模板，还各自改版。

纯正则方案在笔试里能跑通，上线后维护成本会爆炸（每来一个新代理加十条正则，且互相踩）。纯 LLM 方案泛化好但不可控。我的取舍是**规则与 LLM 双轨 + 字段级对账**：

- 规则轨负责"高确定、低语义"的字段（单号、日期、金额、币种），正则 + 表头/列角色推断；
- LLM 轨负责"高语义、低确定"的字段（签发方到底是哪一方、这笔"Destination Charges"该归成哪个标准费用名、材料是否在表达"变更"意图）；
- 两轨冲突时**按字段类别选裁判**：强字段信规则（因为正则命中的字符串是硬证据），弱字段信 LLM（因为语义本来就是它强项），冲突本身记成 `V-RECONFLICT` 并升级。

这里有个我认为值得强调的工程观点：**双轨的价值不在于"两个都跑更准"，而在于"两个不一致时暴露了不确定性"**。单轨系统无论多准，都不会告诉你"这条它自己也没底"。双轨把"模型内部的犹豫"变成了系统外部的可观测信号——这是 harness 工程最便宜的收益点之一。

针对新版式，我的扩展路线是"模板指纹"：按版式聚类（表头词集合 + 列序 + 关键锚点坐标哈希）生成模板 ID，第一次遇到新模板走 LLM + 人审，人审结果沉淀成该模板的列映射，下次直接命中。这样**人工成本随版式数量线性增长，而不是随单据数量增长**——数量是每天几百封，版式是每月几个。

## 6. 幂等性不是加分项，是邮件场景的生存条件

题目输入是 EML——这意味着输入天然会**重复投递**：同一封邮件被转发、被规则重复归档、被 IMAP 重复拉取、用户手动再拖一次。如果系统对同一封邮件跑两次就产生两张账单，这个系统在真实环境里一天就会把账搞乱。

所以幂等必须是设计约束而不是补丁：

```text
幂等键 = (file_sha256, reference_no, charge_item)   # 文件级 + 业务级双层
```

- 文件级：同一份文件重复处理直接命中缓存（`--idempotent`）。
- 业务级：不同文件（比如代理重发的 PDF 和扫描件）抽出同单同费用，也要识别成"同一笔"，而不是两笔 `CREATE`。这正好落在 G5 的跨单重复检测上，两者共用一套判定。

题目没提这一点，但它是"能不能投产"的分水岭。我在 `docs/DEV_SPEC.md §4.10` 把它写成了操作类型的第 7 条规则（`P-IDEMPOTENT` → `NO_CHANGE`）。

## 7. 校验的优先级：先保「不写错」，再保「写得全」

五道闸（金额/币种/勾稽/OCR/重复）不是并列的，我给了不等的处置强度：

| 闸 | 失败后果 | 处置 |
|---|---|---|
| 金额非法、勾稽不平、重复入账 | 错账 | **blocker，阻断入账** |
| 币种非 ISO | 可能只是冷门币种（如 `XAF`、`TWD`），拦了反而添乱 | warn，不阻断 |
| OCR 混淆（名称类） | 影响检索不影响金额 | info |

理由是**假阳性也是有成本的**：把 30% 的正常单拦进人审，财务就会绕过系统直接手工录，系统等于废了。所以"宁多拦不漏拦"只适用在金额类字段上；名称类过度拦截是有害的。

这条我在实现里落成了 `Issue.severity` 三档 + `planner` 只看 severity 不看文案的结构。**校验层输出"严重度"，决策层决定"流转"，两层解耦**——否则每个新规则都要改决策代码，最终变成一坨 if。

## 8. 评测要按错误类型分层，否则指标没有诊断价值

如果只报一个"准确率 92%"，出现回归时无法定位：是解析错了？归一化错了？匹配错了？还是 AR/AP 方向错了？这四类错误的修复成本差一个数量级（改正则 / 改别名表 / 改匹配键 / 改业务规则）。

所以我设计了分层指标（`scripts/evaluate.py`）：

| 层 | 指标 | 定位什么 |
|---|---|---|
| 字段级 | 逐字段 exact-match / P / R / F1 | 哪个字段退化 |
| 记录级 | 一条费用记录全对的比例 | 业务可用率 |
| 操作类型 | CREATE/UPDATE/NO_CHANGE/PENDING 四分类混淆矩阵 | "该更没更" "该拦没拦" |
| 风险召回 | 应拦样本中实际拦住的比例 | 财务安全底线，门禁 ≥95% |
| 幻觉率 | evidence 校验失败字段 / 总字段 | 模型编造倾向 |

并且做成**回归门禁**：字段级 F1 下降 > 2% 或风险召回 < 95% 直接非 0 退出。LLM 类系统最大的工程风险不是"这次不准"，是"不知道比上次差了"——没有门禁的评测只是报表。

## 9. 成本与时延：OCR 是瓶颈，300 秒超时决定了架构

题目给的 OCR 接口 `timeout=(10, 300)`——读取超时 5 分钟，这本身就说明它是重任务（可能是服务端异步解析 + 轮询）。这带来三个工程后果：

1. **不能串行**。100 封邮件串行跑，最坏情况 8 小时。必须批量并发（线程池，上限按网关承受度，默认 4）。
2. **能不走就不走**。文本层 PDF 直接 `pypdf` 抽（毫秒级），只有扫描件才送 OCR。所以我保留了 `--pdf-strategy auto`（默认仍按题意 `ocr`，但生产可切 auto）。这不是偷懒，是把昂贵资源用在真正需要的地方。
3. **必须可缓存**。同一 PDF 在一次批处理里可能被引用多次（邮件 + 附件转存），按 `sha256` 缓存 OCR 结果，避免重复付费。

另外一个常被忽略的成本：**LLM 上下文**。一页 OCR 文本加上表格能到 2-4K token，一封带 5 个附件的邮件直接爆窗口。我的处理是把输入压成"块 + 表"的结构化文本（而不是整页原文），并在超限时按"金额相关行优先"裁剪——**给模型的不是全部信息，是与任务相关的信息**，这比加大窗口更省钱也更准。

## 10. 「不虚构」不能靠提示词，必须靠机器校验

题目第七条反复强调"不得虚构、无法提取用 null、OCR 结果不能未经校验直接入账"。这类要求写进 prompt 是有用的，但**不能作为唯一保证**——LLM 的行为在长尾上不可预测，而"编造一个看起来合理的提单号"恰恰是它最擅长的失败模式。

我把"不虚构"落成两条机器规则：

1. **证据锚定**：LLM 每个字段必须返回原文片段 `evidence`，代码侧校验它是输入文本的子串（去空白归一后）；不匹配 → 字段作废 + `V-UNGROUNDED`。这不是让模型"诚实地说明依据"，而是让**编造在结构上无法通过校验**。
2. **Schema 封闭**：`extra="forbid"` + 固定键集合。模型想加字段、改键名、把金额写成 `"40.00 USD"`，全部在解析层被拒，重试时附上校验错误让它自修。

这两条的价值在于把"提示词的道德要求"翻译成"编译器的类型要求"。**提示词是软约束，schema 是硬约束；生产系统只信硬的。**

## 11. [业务补充] 需求里没写、但真实货代财务一定会问的 8 件事

按"如果我是这个系统的产品负责人，上线前一定会被问到的问题"整理。前 4 条我已在实现里预留了接入点，后 4 条建议纳入下一期。

| # | 问题 | 为什么重要 | 本期状态 |
|---|---|---|---|
| 1 | **多币种与汇率**：一张单里 USD + CNY 混排怎么算？折算用哪天的汇率？ | 货代账单多币种是常态，合计校验跨币种必须折算 | 勾稽校验按"同币种分组"做，跨币种暂不合计（保守）；汇率接入点留在 `normalize/currency.py` |
| 2 | **税额与免税额**：VAT/GST 是否含在 total 里？各国口径不同（如新加坡 GST 另计） | 直接决定勾稽公式 `sum+tax==total` 还是 `sum==total` | 自动探测（有 tax 行则按含税公式），探测不确定时降级为"只校验明细 vs total 二选一" |
| 3 | **粒度问题**：一笔费用挂在"整票"还是"某个箱号"？ | 影响匹配键 T4 与后续分摊 | 保留 `container_no` 字段，本期不做分摊 |
| 4 | **争议与冲销链**：CN 冲的是哪张 DN？是否需要 link 原单？ | 对账必须能追到原单，否则应收应付挂空 | 预留 `related_reference` 字段（本期抽出但只记在 report） |
| 5 | **审批流**：`PENDING_REVIEW` 之后谁审、审完怎么回写？ | 人审闭环没设计，系统就只是个"生成器" | 本期输出 `report.json` 供人审消费，未做 UI/工作流 |
| 6 | **重复计费的时间窗**：同一费用在 30 天内出现两次，是重复还是分期？ | 硬判重复会误杀分期付款 | G5 只做"同单号+同费用+同金额"的严格判重，宽窗口判重待业务确认 |
| 7 | **主数据治理**：`Handling Charge` 的标准名由谁维护？别名表谁改？ | 归一化表是活的资产，需要 owner 和变更流程 | 别名表外置为 YAML，支持热加载；无审核流程 |
| 8 | **导出对接**：财务系统要什么格式（SAP IDoc / 金蝶 / 用友 / 自研 API）？ | 决定"标准结构化数据"的最终形态 | 本期只出 JSON，转接层留白 |

另外补一个**合规视角**：财务数据的处理依据必须可回溯（谁在什么时候基于什么原文做了什么判断）。所以我把 `provenance`（字段级原文片段 + 页码 + 行号）和 `trace`（每次运行的阶段日志）做成了必然产物，而不是调试开关——**审计能力不能是可选项，因为它一旦被关掉就再也补不回来了**。

## 12. [落地后补] 真实数据的价值不是"验证通过"，是"证伪"

写这份文档时我给的是 11 条思考；拿到题目网盘的真实附件后，第 12 条是被数据打出来的。

**合成样本永远会通过它自己的测试。** 第一版在 `data/samples` 上 10 条记录全对、122 项测试全绿、评测 F1 = 1.000。换成真实数据（1 封邮件 + 2 份 PDF + 1 张扫描图），立刻出现：

- 33 条记录、全部 `PENDING_REVIEW`，明细合计 4.07 亿 vs 单据总计 1410.40；
- 提单号 `260801188`、银行路由号 `121000358`、邮编 `7032` 都被当成金额；
- 签发方抽成了 `SHIPPER`（货物关系方），不是出单人。

原因很简单：**样本是我按自己的正则写的版式生成的，它证明的只是"正则和样本自洽"。** 真实单据是别人按他们的业务系统导出的，`D/C No.`、`CHARGES CUR AMOUNT`、单空格对齐的 `HANDLING CHARGE - 65.00 1.00 C 65.00`，没有一条是我预设的形态。

由此得到三条更硬的经验：

1. **"抽得全"和"抽得准"在真实数据上是矛盾的**。全文档扫行能把所有金额都抓到，但掺进一半是地址、电话、账号。解决办法不是加更多正则，而是**先定位语义区块**（费用表头 → 合计行），把搜索空间从"整页"缩到"几行"。这是结构约束，不是模式匹配。
2. **评测集必须来自外部**。自建金标只能证明"我按我的理解实现了"，跑分再高也只是自证。真实数据一进来，指标从 1.000 掉到 0（第一轮全被拦），这才是真实的起点。
3. **拦住比抽对更重要，但不能靠"全拦"交差**。第一轮 33 条 `PENDING_REVIEW` 看着"很安全"——其实是无能：全部拦截等于没有系统。合格的边界是**该抽的抽对、该拦的拦住**：Debit Note 的 3 条费用要能自己对齐总计 1410.40，而扫描件拿不到 OCR 时必须老实进 `errors.json`。

最后补一句对"不得虚构"的理解：真实数据里那张 ZIM 扫描件我确实读得出来（人工看图能读出 `ORFR1618731`、26.90 USD），但**读得出来不等于系统跑出来了**。所以它在 `docs/REAL_DATA_NOTES.md` 里以"人工核对基准"的身份出现，而 `result.json` 里一条都没有——**能用眼睛补的，不能用代码假装**。

## 13. [落地后补] 「更先进的技术」不等于「更好的结果」

第 12 条讲真实数据会证伪设计；这一条是它的续集，证伪的是我对技术路线的直觉。

我原来的假设是：**OCR 是比 PDF 文本层更强的路径**——毕竟 OCR + 大模型是"现代做法"，文本层是"老办法"。
所以 `pdf_strategy` 默认 `ocr`，OCR 成功就覆盖文本层。

拿到四份 PDF 的真实网关响应后，这个假设在同一份 Debit Note 上翻车：

| 字段 | 文本层 | 网关 OCR |
|---|---|---|
| 单号 | `DC-108478` | **空** |
| 币种 | USD | **空**（`chargeList` 压根没有币种字段） |
| 明细 | 65 + 1310.40 + 35（3 条） | 100 + 1310.40（2 条，**65 和 35 被合并**） |
| 合计 | 1410.40 | 1410.40 |

总额都对。但入账要的是明细和单号——**「总额对」不等于「能入账」**。
如果当时让 OCR 覆盖文本层，这条账单会丢单号、丢币种、两笔费用挤成一条，
而且因为没单号还会被判成 CREATE 重复入账。所有这些都是"跑通了、返回 success: true"的表象之下发生的。

这件事我想记下三点：

1. **"success: true" 只说明链路通了，不说明数据对。** 网关返回 200、`文档处理成功`、字段结构完整，
   但核心字段是空的。判断质量必须看字段级对比，不能看接口返回码。
2. **合并是不可逆的信息损失。** 65 + 35 = 100 在数值上无损，在语义上有损——谁付的、按什么规则收的，
   这些在入账和后续对账时都要用。凡是"聚合"都该问一句：聚合掉的是噪声还是证据。
3. **两条路都跑，比选一条更省事。** 我一开始在纠结"到底用 OCR 还是文本层"，实际上两者各有强项：
   文本层给精确的单号/币种/明细，OCR 给结构化的箱号列表（它一次给了两个，文本层只抠出一个）。
   最后落成「文本层为主、OCR 补标识」，比任何单一路线都好。

反过来也要说清：这个结论**只对这类电子版账单成立**。如果是传真件、拍照、扫描件，根本没有文本层，
OCR 就是唯一选择——而那张 ZIM 扫描件正是这样跑通的（26.90 完全正确）。
所以不是"OCR 不好"，是**"有文本层时不该让 OCR 覆盖它"**。

## 14. [被质询后补] 「3 条 AP」和「0 条 AP」，哪个是更好的结果？

有人看了真实数据全 `PENDING_REVIEW`，问：这不是等于 AR/AP 没实现吗？

这个问题逼着我回头查了一遍，结果发现一个更难看的事实：**上一版那 3 条 AP 是错的。**

### 14.1 那 3 条 AP 是怎么来的

`recipient` 抽成了 `PltPlt`，依据是 Debit Note 页脚这三行：

```
NEPTUNE SHIPPING LIMITED (LAX) Powered by
|
湃乐多（上海）航运科技有限公司
Pilot Aiship Tech co., Ltd.
```

`Powered by 湃乐多` 是**单据系统的水印**——NEPTUNE 用了湃乐多的 SaaS，不是说这张单开给湃乐多。
把它当接收方，判向就正好反过来：我方从「不相干」变成了「付款人」。

因为当时加了 `F-PARTY_INFERRED` blocker，这条错误被拦在了 `PENDING_REVIEW`，
没有真的入账。但**字段本身是错的**：`report.json` 里白纸黑字写着 `recipient: "PltPlt"`。
换一个不检查 issue 的下游，这就是一笔错账。

### 14.2 我的两个判断都错了

- 错在**把水印当交易方**：只判断了「主体名是否出现在单据上」，没判断「出现在什么位置」。
  备注句我排除了（上一轮修的），水印区没排除。
- 错在**用「有没有产出 AR/AP」当质量指标**：3 条 AP 看着比 0 条有说服力，于是我没有质疑它们的依据。

第二条更危险。如果评审只数「自动入账了几条」，那最容易拿分的做法就是多猜——
猜对了算准确率，猜错了靠 blocker 兜。这种系统跑分很好看，但它是**靠兜底在假装准确**。

### 14.3 怎么证明「不是做不到」

被质疑「AR/AP 没实现」时，光解释不够，得给出可复现的证据。我做了一个换主体的实验：

| 记账主体 | posting | operation |
|---|---|---|
| PltPlt | null | PENDING_REVIEW |
| AEBO TCO IMPORT LLC | AP | PENDING_REVIEW（推断接收方） |
| **NEPTUNE SHIPPING LIMITED** | **AR** | **CREATE（自动入账）** |

同一份 PDF、同一套代码，主体换成签发方自己，立刻判出 `AR + CREATE` 并自动入账。
加上合成样本的 `AR 2 / AP 8`、旧格式样本的 `AR 4`，一共三条自动判向路径。

**结论：判向逻辑没问题，是这 4 份文件确实不是「我方」的账。**

### 14.4 留给自己的规矩

1. **「能自动判多少条」不是好的质量指标**，好的指标是「判出来的那些对不对 + 判不出的理由清不清楚」。
   前者会诱导多猜，后者要求把边界说透。
2. **同一个字段，位置比内容更重要。** `湃乐多` 出现在「Powered by」后面和出现在「BILL TO」后面，
   是两个完全相反的意思。抽取层如果只看「这个字符串在不在文中」，就一定会踩这种坑。
3. **被质疑时先自查，别先辩解。** 这次如果直接回「因为数据里没有交易方」，就永远发现不了那 3 条 AP 是错的。
